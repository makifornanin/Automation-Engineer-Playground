# AEP Observability Standard

## Purpose

AEP uses structured execution logs so learners can understand what happened inside an automation without relying only on raw n8n execution history.

The future AEP website will render these records as an execution timeline.

## Standard Log Contract

Each log record can contain:

- workflow_name
- execution_id
- event_id
- status
- stage
- error_message
- retry_count
- recovered
- metadata
- logged_at

## Example

```json
{
  "workflow_name": "AEP Lab 08 - Dead Letter Queue & Failure Recovery",
  "execution_id": "3945",
  "event_id": "evt_observe_003",
  "status": "recovered",
  "stage": "recovery_completed",
  "error_message": null,
  "retry_count": 3,
  "recovered": true
}
```

## Storage

Lab 08 writes these records to Supabase. Create the table before running that
lab:

```sql
create table if not exists execution_logs (
  id bigint generated by default as identity primary key,
  workflow_name text,
  execution_id text,
  event_id text,
  status text,
  stage text,
  error_message text,
  retry_count integer,
  recovered boolean default false,
  metadata jsonb,
  logged_at timestamptz not null default now()
);
```

Every column is nullable except the primary key and `logged_at`. A log record
should never be the reason a workflow fails.

## What the Fields Mean

| Field | Why it exists |
|---|---|
| `workflow_name` | Which automation produced this — set it from `{{ $workflow.name }}` |
| `execution_id` | Ties the record back to one n8n run, via `{{ $execution.id }}` |
| `event_id` | The business identity of the work, so you can trace across runs |
| `status` | Where it ended up: `failed`, `recovered`, `processed` |
| `stage` | Which point in the flow wrote this, e.g. `dlq_queued` |
| `error_message` | Why it failed. Leave empty on success |
| `retry_count` | How many attempts were used before this outcome |
| `recovered` | Whether the work was eventually completed |

`execution_id` and `event_id` do different jobs, and the difference is the whole
point. One run has one `execution_id`. One business event may be retried,
queued and replayed across *several* runs — but it keeps the same `event_id`
throughout.

## Tracing an Event

Given an event ID, its full history is one query:

```sql
select logged_at, workflow_name, execution_id, status, stage,
       error_message, retry_count, recovered
from execution_logs
where event_id = 'evt_dlq_001'
order by logged_at;
```

Reading the rows top to bottom answers the five questions that matter:

```text
What happened      -> status + stage
When               -> logged_at
Where it failed    -> stage of the failing row
Why                -> error_message
Did it recover     -> a later row with recovered = true
```

Without `event_id`, n8n's execution list shows you a failed run and a separate
successful one, with nothing connecting them. With it, you get a story.

## Never Log Secrets

Log identifiers and outcomes, never payload contents that may hold credentials,
tokens or personal data. `event_id` is safe; a whole request body is not.

## Where This Goes Next

Lab 08 is where these records first get written, because a dead letter queue is
useless if you cannot tell *why* something landed in it. The Capstone reuses the
same contract across every stage — intake, AI decision, routing, approval,
failure — so one `event_id` traces a request through the entire system.

The future AEP Website renders these rows as an execution timeline, which is why
the field names are worth keeping stable.
