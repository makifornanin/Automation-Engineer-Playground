# Lab 10 - AI Guardrails & Human-in-the-Loop

## Goal

Learn when AI should be allowed to trigger an action automatically and when a human should take control.

This lab builds on Lab 09.

Lab 09 taught:

```text
AI
→ structured output
→ validation
→ routing
```

Lab 10 adds:

```text
AI recommendation
→ permission rules
→ confidence threshold
→ automatic action OR human approval
```

---

## Main Learning Outcome

Understand that:

> AI confidence and permission are not the same thing.

An AI model can be highly confident about an action that should still require human approval.

Example:

```text
AI recommends: cancel_account
Confidence: 1.00

But cancel_account is restricted.

Result:
→ Human approval required
```

---

# Business Scenario

A business receives service requests.

Gemini recommends one action:

```text
send_to_sales
create_support_ticket
send_to_billing
issue_refund
cancel_account
manual_review
```

Some actions are safe enough to run automatically.

Others are restricted.

---

# Guardrail Rules

## Allowed Automatic Actions

```text
send_to_sales
create_support_ticket
send_to_billing
```

## Restricted Actions

```text
issue_refund
cancel_account
```

## Confidence Threshold

```text
0.85
```

Automatic execution is allowed only when:

```text
action is allowed automatically
AND
confidence >= 0.85
AND
action is not restricted
```

Otherwise:

```text
human approval required
```

# Main Workflow

```text
Receive Service Request
↓
Prepare Guardrail Input
↓
Gemini Guardrail Decision
   ↳ Google Gemini Chat Model
   ↳ Structured Output Parser
↓
Apply Guardrails
↓
Can Auto Execute?
│
├── TRUE
│   ↓
│   Execute Automatic Action
│   ↓
│   Respond to Webhook
│
└── FALSE
    ↓
    Create Pending Approval
    ↓
    Return Pending Approval
    ↓
    Respond to Webhook
```

# Approval Storage

Supabase stores pending and completed approval requests.

```sql
create table public.approval_requests (
  id bigint generated by default as identity primary key,
  request_id text not null,
  recommended_action text not null,
  confidence numeric not null,
  reason text,
  status text not null default 'pending',
  human_decision text,
  created_at timestamptz not null default now(),
  decided_at timestamptz
);
```

# Gemini Decision

Gemini returns structured output such as:

```json
{
  "recommended_action": "send_to_billing",
  "confidence": 1,
  "reason": "The request concerns a billing problem."
}
```

Gemini only recommends an action.

It does not decide whether that action is authorized to run automatically.

---

# Apply Guardrails

The guardrail layer checks:

```text
Is the action allowed automatically?
Is the action restricted?
Is confidence high enough?
```

It produces fields such as:

```json
{
  "is_allowed_automatic": true,
  "is_restricted": false,
  "high_confidence": true,
  "can_auto_execute": true,
  "requires_approval": false,
  "guardrail_reason": "automatic_action_allowed"
}
```

---

# Automatic Path

Example:

```text
recommended_action = send_to_sales
confidence = 1.00
```

Because:

```text
send_to_sales = allowed
confidence >= 0.85
not restricted
```

the workflow returns:

```json
{
  "success": true,
  "status": "auto_executed",
  "action": "send_to_sales",
  "requires_approval": false,
  "decision_source": "ai_guardrail"
}
```

---

# Restricted Action Path

Example:

```text
recommended_action = cancel_account
confidence = 1.00
```

Even though confidence is high:

```text
cancel_account = restricted
```

therefore:

```text
can_auto_execute = false
requires_approval = true
```

The request is stored in Supabase with:

```text
status = pending
```

---

# Low-Confidence Path

Example:

```text
recommended_action = send_to_sales
confidence = 0.60
```

`send_to_sales` is normally allowed.

But:

```text
0.60 < 0.85
```

therefore:

```text
requires_approval = true
```

This demonstrates:

> An allowed action can still require human review when AI confidence is too low.

---

# Human Approval

A human decision is sent to the second webhook.

Example:

```json
{
  "approval_id": 1,
  "decision": "approve"
}
```

> **Use your own ID, not this one.** `1` is only an example. The
> `approval_requests` table assigns `id` in insert order, so the pending record
> created by *your* run will usually have a different number.
>
> Find yours in the Supabase table editor, or run:
>
> ```sql
> select id, request_id, recommended_action, status
> from approval_requests
> where status = 'pending'
> order by id desc;
> ```
>
> The `approval_id` values in `sample-data/approve-decision.json` and
> `sample-data/reject-decision.json` are placeholders — replace them with your
> own pending IDs before testing.
>
> The future AEP Website will resolve this automatically, because the approver
> will click a real pending request rather than type an ID.

The workflow fetches only:

```text
id = <the approval_id you sent>
AND
status = pending
```

This prevents already-decided approvals from being processed again.

---

# Approved Path

When the human approves:

```text
status = approved
human_decision = approved
decided_at = timestamp
```

The workflow then resumes and executes the approved action.

Example response:

```json
{
  "success": true,
  "status": "approved_and_executed",
  "action": "cancel_account",
  "human_decision": "approve"
}
```

---

# Rejected Path

When the human rejects:

```text
status = rejected
human_decision = rejected
decided_at = timestamp
```

The restricted action is not executed.

Example:

```json
{
  "success": true,
  "status": "rejected",
  "action": "cancel_account",
  "human_decision": "reject"
}
```

# Important Debugging Lessons

## Wrong Gemini Recommendation

Gemini initially interpreted:

```text
"Please cancel my account."
```

as:

```text
create_support_ticket
```

The guardrail correctly allowed that recommendation because it was an allowed action.

The lesson:

> Guardrails can only evaluate the recommendation they receive.

The Gemini prompt was improved so explicit cancellation requests map to:

```text
cancel_account
```

while the guardrail remains responsible for authorization.

---

## No Output from Pending Approval Lookup

An already-approved record was queried using:

```text
id = 1
AND
status = pending
```

Because the record was already:

```text
status = approved
```

Supabase correctly returned no row.

This prevents duplicate decisions.

---

## Timestamp Error

The approval update initially attempted to send:

```text
"approved"
```

into a timestamp field.

Correct mapping:

```text
status = approved
human_decision = approved
decided_at = current timestamp
```

# Important Engineering Principles

## Confidence Is Not Permission

```text
High confidence
≠
Authorized action
```

## AI Recommends, Guardrails Authorize

```text
Gemini
→ recommendation

n8n guardrails
→ permission decision
```

## Risky Actions Need Human Control

Sensitive actions such as cancellation or refunds should not run automatically simply because AI is confident.

## Persist Pending Decisions

Human approval may happen later, so the request needs durable storage.

## Prevent Double Decisions

Only records with:

```text
status = pending
```

should be eligible for approve/reject processing.

# Final Takeaway

Safe AI automation follows this pattern:

```text
AI RECOMMENDS
↓
GUARDRAILS CHECK
↓
IS IT ALLOWED?
↓
IS CONFIDENCE HIGH ENOUGH?
↓
AUTO EXECUTE OR HUMAN REVIEW
↓
SAVE THE DECISION
```

AI can help decide what might be useful.

The automation system decides what is actually permitted.
